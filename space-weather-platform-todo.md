## 5. Superposed epoch analysis (SEA)

- [x] Assemble the event catalog (storm onset times, CME arrival times) as a static dataset in S3 — `scripts/backfill_donki_gst.py`; 200 storms, 2010-04-05 through present (DONKI's actual coverage start, confirmed by probing — see script docstring). Curated catalog includes onset time, peak Kp + G-scale class, and linked CME activity IDs. Validated against the well-documented May 2024 "Gannon storm" (correctly G5, max Kp=9.0, linked to its 5 known source CMEs). Note: DONKI coverage doesn't reach back to 2010 the way OMNIWeb does to 1963 — decided 2026-09-15 to accept 2010+ scope rather than add a manual pre-2010 supplement or research an alternate deep-history catalog
- [x] Write the core SEA function: given an event list and a window size, extract and align time-series segments on epoch time — `sea/alignment.py`, source-agnostic (`{timestamp: value}` + a plain event list, no dependency on the DONKI/OMNIWeb schemas). Rounds event times to the nearest hour to match the OMNIWeb series' hourly cadence — needed in practice, since 12 of the 200 real DONKI onset times aren't exactly on the hour
- [x] Decide on normalization approach (raw values vs. deviation from baseline vs. normalized amplitude) — `sea/normalization.py`; deviation-from-baseline is the default (standard in the SEA literature, keeps results in physical units), raw and normalized-amplitude are available as alternates via the same call signature (default baseline window: hours -48 to -6 relative to onset)
- [x] Implement aggregation (mean, median, percentile bands) across aligned events — `sea/aggregation.py`; per-offset mean/median/configurable percentiles (default 25/75), missing values excluded rather than treated as zero, percentile interpolation matches numpy's default convention
- [x] Package as a Fargate task or Glue Python shell job (pandas/numpy/scipy) — Glue Python shell chosen over Fargate: the workload (align/normalize/aggregate ~200 events against a few small Parquet files) needs no Docker/VPC/ECR overhead, fits the smallest Python shell size (0.0625 DPU). `sea/run_sea_job.py` is the entrypoint (plain argparse, runs identically locally or in Glue), packaged via `infra/stacks/sea_stack.py`; no pandas/numpy/scipy needed since the core logic is stdlib-only
- [x] Add a Step Functions state to trigger SEA runs on a schedule or on-demand via API — `SeaStateMachine` wraps a `GlueStartJobRun` task inside a `Map` state, triggered weekly via EventBridge; on-demand today via `aws stepfunctions start-execution`, a proper HTTP trigger is section 7's job once API Gateway exists. **Updated 2026-09-16**: originally ran only `dst_index`/`raw` (a hardcoded pair in the job's `default_arguments`) — the compute logic (`sea/run_sea_job.py`, `sea/normalization.py`'s 3 `STRATEGIES`) already supported any of the 16 queryable fields x all 3 normalizations, only the orchestration was hardcoded to one combination. Changed to a `Map` state iterating over the full 16x3=48 combination matrix (`SEA_COMBINATIONS` in `infra/stacks/sea_stack.py`), `MaxConcurrency=8`, with the Glue job's own `ExecutionProperty.MaxConcurrentRuns` raised to match (Glue caps concurrent runs of one job at 1 by default). Hit and fixed a real race on the first backfill attempt: firing 8 concurrent `StartJobRun` calls occasionally beats Glue's own admission-count update when a slot frees up mid-batch, throwing `Glue.ConcurrentRunsExceededException` for one call and aborting the whole `Map` (confirmed via `get-execution-history` + `get-job-runs`: 2 of 48 combinations had already succeeded and written to S3 before the abort) — fixed with a retry-with-backoff on that specific error (`add_retry`) rather than reducing concurrency. Backfilled all 48 combinations via one manual `start-execution` (~7 minutes); no API or frontend changes needed since both were already built generic (`lambdas/api/sea_results.py` validates against the full lists and 404s gracefully for anything not yet computed, `SeaVisualization.jsx`'s dropdowns already offered the full lists).
  - **Extended 2026-09-16**: added `bx_gsm`/`bx_gse` to the queryable field list (16→18 fields, 48→54 combinations). These are the one queryable field that isn't a 1:1 Parquet column match — GSE and GSM share the same X-axis by definition (both point Earth-to-Sun; only Y/Z differ, rotated about that shared axis), so OMNI2 only publishes a single physical `bx_gse_gsm` column, unlike By/Bz which really do differ between frames. Exposed as two separate fields anyway (user's call, for display symmetry with By/Bz) via a `FIELD_COLUMN` mapping duplicated in both `lambdas/api/historical.py` and `sea/load_data.py` — both fields read the same column and always return numerically identical values, by design, not a bug. Required rebuilding and redeploying the `sea_lib` wheel (`infra/stacks/sea_stack.py`'s `DeploySeaLib`) since `load_data.py` is packaged into it. Backfilled the 6 new combinations (~8 minutes). Caught one real gap post-deploy: `lambdas/api/sea_results.py` has its own separate hardcoded `VALID_FIELDS` copy that didn't get updated alongside `historical.py`'s, so `/sea/bx_gsm/...` 400'd as "unknown field" even with the result already computed and sitting in S3 -- fixed and redeployed. Swept the rest of the codebase for other hardcoded copies of this field list (`ml/features.py` and `lambdas/ingestion/handler.py` both reference `bz_gsm` but are unrelated: the former is a deliberately curated ML feature-selection list, the latter is a different real-time feed's schema) -- no other gaps found.
- [x] Write unit tests using a synthetic dataset with known events (verify alignment logic is correct) — `sea/tests/test_alignment.py`; plants an identical known V-shaped signature at three unrelated absolute event times and confirms alignment recovers it exactly at each, plus hour-rounding and missing-data edge cases
- [x] Validate SEA output against a published space-physics result as a sanity check (e.g., known Dst index storm signature) — `sea/validate_dst_signature.py`; ran the real pipeline (200 real DONKI storms x real OMNIWeb Dst, raw mode) end-to-end. ## 6. ML forecasting pipeline
